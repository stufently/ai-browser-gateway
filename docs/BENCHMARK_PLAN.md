# План замера (фаза 1)

Задача фазы: выбрать 2–4 способа доставать страницы **по измеренным числам**, а не
по описаниям. Результат фазы — таблица в `docs/research/`, а не рассуждение.

## Два стенда, и они меряют разное

Их нельзя смешивать в одной колонке.

**Стенд A — локальный детерминированный сервер (`bench/server`).** Меряет
СПОСОБНОСТИ: выполняет ли провайдер JS, видит ли Shadow DOM, держит ли сессию,
сколько стоит холодный старт. Не зависит от сети и чужих настроений,
воспроизводится побайтно, гоняется сколько угодно раз.

**Стенд B — боевые цели (`bench/targets/targets.toml`).** Меряет ПРОХОДИМОСТЬ:
пускает ли Cloudflare. Шумный по своей природе, единичные запросы, повтор не
воспроизводит результат.

Провайдер, прошедший стенд A на 100 % и не берущий ни одной цели стенда B,
бесполезен. Обратное тоже верно. Поэтому колонки в отчёте раздельные.

## Признак успеха

**HTTP 200 успехом не считается.** Страница-заглушка Cloudflare приходит с 200,
и её HTML длиннее настоящего. Успех — это найденный **sentinel**: на стенде A
уникальная строка вида `ABG_TEST_JS_OK`, на стенде B — поле `expect` цели.

Отсюда же следует, что провайдер обязан отдавать не «ок», а нормализованный
результат, по которому проверку делает раннер, а не сам провайдер.

## Сценарии стенда A

| # | Сценарий | Что различает |
|---|---|---|
| 1 | статический HTML | накладные расходы провайдера, нижняя граница |
| 2 | цепочка редиректов | итоговый URL, куки по дороге |
| 3 | gzip + brotli | корректность декомпрессии |
| 4 | sentinel вставляется JS после загрузки | HTTP-класс против браузерного |
| 5 | SPA: навигация + fetch + правка DOM | «дождался ли реального рендера» |
| 6 | sentinel в same-origin iframe | доступ к фреймам |
| 7 | sentinel в ЗАКРЫТОМ Shadow DOM | `document.querySelector` его не видит; нужен CDP-граф |
| 8 | сессия: запрос A ставит куку, запрос B её требует | переиспользование контекста |
| 9 | детерминированные 403 / 429 / 503 | классификация отказа без эскалации в браузер |
| 10 | медленный ответ | обработка таймаута |
| 11 | JS бросает исключение | «страница не открылась» ≠ «открылась, JS упал» |
| 12 | большой DOM | память, скорость извлечения, размер выдачи |

Сценарий 7 выбран не для красоты: закрытый Shadow DOM — ровно то место, где
`gpt-web-gateway` ищет виджет Turnstile, и там же сломалась его первая диагностика
(`document.querySelectorAll('iframe')` вернул `[]` на странице с видимым виджетом).
Провайдер, не видящий сквозь закрытый корень, не сможет обслужить челлендж.

## Что записывается на каждый запуск

`provider`, `provider_version`, `scenario` либо `target`, `run_id`, `cold|warm`,
`success`, `sentinel_found`, `status`, `final_url`, `challenge_type`,
`elapsed_ms`, `startup_ms`, `cpu_ms`, `peak_rss_mb`, `bytes`, `redirects`,
`error_type`, плюс воспроизводимость: дата, ядро, версия Docker, версия образа,
egress-IP и ASN.

Egress пишем не для красоты. У `gpt-web-gateway` измерено 26.07.2026: **один и
тот же образ** с одним отпечатком получает 200 с одного адреса и
`403 cf-mitigated: challenge` с другого. Строка замера без egress ничего не
доказывает.

## Холодный и тёплый

Браузерные провайдеры разделяются на `cold` (процесс поднимается) и `warm`
(процесс живёт, переиспользуется контекст). Это разные деньги в проде. Минимум
10 холодных и 30 тёплых на пару провайдер×сценарий, число настраивается.

## Incremental coverage — главный выход

Не «у кого success rate выше», а **что этот провайдер добавляет к уже выбранным**.
Провайдеры сортируются по стоимости от дешёвого к дорогому; для каждого считается
множество ячеек (сценарий×цель), которые он берёт, а все более дешёвые — нет.

Правило отбора: провайдер остаётся, только если даёт **≥5 % относительного
прироста покрытия ИЛИ закрывает класс, который не закрывает никто**. Порог
настраиваемый, а не научная истина.

Отдельная колонка — `unique wins`: ячейки, которые берёт ТОЛЬКО он. Провайдер с
нулевым incremental, но ненулевым unique — это провайдер, стоящий не на своём
месте в порядке цены.

## Что мерить нельзя и как это оформляется

Платные API и прокси: замера не будет (решение владельца — карту не трогаем).
В сводной таблице их success rate — **пустая ячейка с пометкой «не измерено»**.
Подставлять туда заявленные вендором 99,9 % запрещено: это величина другой
природы, и в одном столбце с нашим замером она превращается в ложь.

## Порядок

1. Ядро харнесса: модели, сценарии, WSGI-сервер стенда A, счётчик покрытия,
   рендер отчёта. Всё чистое, без сети и Docker — **веха M1, исполнитель Grok**.
2. Контракт провайдера в контейнере + первые образы: `curl`, `httpx`,
   `curl_cffi`. Стенд A прогоняется целиком — веха M2.
3. Браузерные провайдеры: ванильный Playwright (контроль), patchright,
   camoufox, pydoll — веха M3.
4. Стенд B: боевые цели, единичные запросы.
5. Сервисы-эталоны (`FlareSolverr`, `Byparr`, `trawl`) и обходные входы
   (RSS, sitemap, JSON-эндпоинты, Wayback, Common Crawl).
6. Прайс-разведка платных. Сводная таблица и выбор 2–4 победителей.
