# Рабочий журнал `ai-browser-gateway`

Единственный источник правды по статусу работ. Изменения кода/поведения — в
`CHANGELOG.md`, сюда не дублируются. Записи старше ~30–60 дней уезжают в
`docs/worklog-archive/YYYY-MM.md`.

## IN_PROGRESS

- [ ] **Веха M5 — прокси и `environment_error`.** Спека `docs/specs/m5-proxy.md`,
  исполнитель Grok, панель `gk-abg-m5-proxy`. Ревью и мутации — Codex.
  Делает шаг `change_egress` исполнимым: профили из файла вне репозитория
  (`~/.config/abg/proxies.toml`, права 0600), значение уезжает в контейнер через
  `--env ИМЯ` без значения в argv (проверено), запись хранит только имя профиля.
  Вторая половина — отличить «сломались мы» (коды docker 125/126/127) от
  «не пустила цель»: в прогоне M4 образ с чужим тегом дал `provider_error`, и по
  записи это неотличимо от упавшего пробника.
  **Проверить на приёмке своим тестом (в спеке не закрыто):** файл профилей с
  правами шире `0600` даёт `environment_error` (наша ошибка), а не падение
  прогона и не «прокси не помог». Три состояния обязаны различаться: файла нет →
  `not_measured`; права широки → `environment_error`; профиль применён и цель не
  поддалась → результат замера. И поправить в спеке формулировку про секрет:
  форма `--env ИМЯ` убирает значение ИЗ ARGV, но оно остаётся в окружении
  раннера, в `/proc/<pid>/environ` его детей и в `docker inspect` — «не в argv»
  не равно «не видно в системе».
- [ ] **Веха M6 — правило отбора по нескольким измерениям.** Измерено, что
  incremental coverage **зависит от порядка перебора** и не видит свежесть:
  архив 431,86 ч против ленты 0,02 ч на одной цели, и при одном порядке лента
  получает «исключить». Прежде чем чинить, перечислить ВСЕ измерения, по которым
  провайдеры отличаются (покрытие, свежесть, стоимость, стабильность), и решить,
  какое правило оптимизирует, а какие остаются ограничениями. Обязателен тест,
  который гоняет один набор в ДВУХ порядках и требует одинакового вердикта — он
  ловит этот класс, не зная, какое измерение забыли.

## За владельцем (я сам сделать не могу)

- [ ] **Токен Cloudflare API + поддомен под свой стенд.** Домен — из тех, что уже
  в Cloudflare и ведутся через octodns (`~/github/ansible`, репо octodns); запись
  кладётся штатным флоу octodns, не руками в панели. Даёт воспроизводимый
  CF-стенд: Managed Challenge и Turnstile на официальных тестовых ключах. Пока
  токена нет — фаза 1 идёт на чужих целях, стенд подключается позже.
- [ ] **Токен Cloudflare для Browser Run.** Аккаунт CF у владельца уже есть, значит
  managed-браузер от самого Cloudflare открывается API-токеном: 10 browser-hours в
  месяц включено, дальше $0,09/час ≈ $0,25 за 1000 страниц. Без токена строка
  остаётся «не измерено».
- [ ] **Креды GoldProxy.** Самый ценный незакрытый замер фазы 1: наш хост сидит на
  хостинговом ASN без репутации (`AS206996 ZAP-Hosting`), и **отличить «инструмент
  не справился» от «адрес не пустили» без второго egress нельзя**. У gpt-web-gateway
  это уже измерено: один образ, один отпечаток, разные адреса — 200 и 403.
- [ ] **Живой URL рилса для цели `login-instagram`.** Я подставил id наугад, и
  замер это поймал: все провайдеры получили тайтл `Post isn't available` — строка
  меряет мёртвую ссылку, а не стену авторизации, и помечена `valid = false`. Нужен
  конкретный публичный рилс из тех трёх задач бэклога, ради которых цель и взята.
- [ ] **Какие ещё боевые цели из рабочих проектов добавить.** Сейчас взяты
  `bizprofile.net` (снят с мониторинга check-sites из-за CF, возврат намечен на
  12.09.2026), `instagram.com` (три задачи бэклога упираются в стену логина) и
  магазины hqd как контроль «чистый nginx».
